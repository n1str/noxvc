# Развёртывание

English: [en/deployment.md](en/deployment.md)

## Какие порты нужны снаружи

| Порт | Протокол | Для чего |
|---|---|---|
| 80 | TCP | Переход HTTP → HTTPS, проверка Let's Encrypt |
| 443 | TCP | Веб-клиент, `/api`, `/gateway` (WebSocket), файлы; на голосовом домене — сигнализация LiveKit |
| 7882 | UDP | Медиа WebRTC (всё на одном порту) — основной путь |
| 7881 | TCP | Медиа WebRTC по TCP — запасной путь, если UDP закрыт |
| 3478 | UDP | TURN (клиенты за строгим NAT) |

Остальное (PostgreSQL, Garage, API LiveKit 7880, метрики 9464/6789, Grafana 3000) — только внутри сети Docker или
на `127.0.0.1`.

`PUBLIC_IP` — адрес, по которому клиенты достают сервер: LiveKit вписывает его в ICE-кандидаты. Если он неверный,
голос «подключается» (сигнализация работает), но звука нет.

## Обратный прокси

### Caddy (входит в комплект)

`docker compose --profile https up -d` запускает Caddy с [`deploy/Caddyfile`](../deploy/Caddyfile): сертификаты сами,
HTTP → HTTPS, HSTS, сжатие, проксирование WebSocket. Два сайта:

- `APP_DOMAIN` → `relay:8080`;
- `VOICE_DOMAIN` → `livekit:7880`.

### Свой nginx

Запускайте без профиля `https`, оставьте `HTTP_BIND=127.0.0.1:8080` и `LIVEKIT_SIGNAL_BIND=127.0.0.1:7880` и
проксируйте оба имени (сертификаты — например, certbot). Готовый конфиг — в английской версии:
[en/deployment.md](en/deployment.md#nginx-your-own). Главное:

- `X-Forwarded-For` — **перезаписывать** адресом клиента, а не дописывать: сервер берёт первое значение (журнал
  сеансов, ограничения частоты);
- `X-Relay-Region` — очищать (внутренний заголовок);
- для `/gateway` и голосового домена — заголовки `Upgrade`/`Connection` и долгий `proxy_read_timeout`;
- `client_max_body_size 30m` (вложения до 25 МБ).

## TURN

Встроенный TURN LiveKit слушает UDP 3478 под именем `VOICE_DOMAIN`. Клиенты используют его сами, если прямой UDP не
проходит. TURN поверх TLS (для сетей, где открыт только HTTPS) в стандартной конфигурации не включён — при
необходимости см. документацию LiveKit (`turn.tls_port`, сертификат для имени TURN).

## Домашний сервер за роутером

Пробросьте порты из таблицы выше с WAN-интерфейса роутера на сервер. Важно:

- **Правила проброса — только для WAN-интерфейса** (или публичного адреса). Правило без этого перехватывает и трафик
  из вашей сети на эти порты к *любым* адресам в интернете.
- **Hairpin NAT**, если открываете домен из той же сети: устройства дома получают публичный IP и роутер должен
  завернуть этот трафик обратно на сервер (и маскировать его, чтобы ответы шли через роутер). Другой вариант —
  локальный DNS, который отдаёт домашним устройствам LAN-адрес сервера.
- Проверьте, что никакое правило маскарадинга не подменяет адрес *входящего* проброшенного трафика — иначе сервер
  видит всех как роутер, и журнал сеансов, геолокация и ограничения по IP перестают работать.

## Несколько серверов

У сервера есть необязательный режим нескольких узлов (`RELAY_REGIONS_FILE`: дополнительные точки входа HTTPS и
TURN-релеи в других регионах, которые ведут на один основной сервер). Одному серверу он не нужен и в compose не входит.
